# [ADR-0001] Використання Layered Architecture

- **Статус:** Прийнято (Accepted)

## Контекст та постановка проблеми

Для розробки застосунку «Електронний журнал» необхідно обрати архітектурний підхід, який забезпечить чітке розмежування відповідальності, простоту тестування та легкість підтримки коду.

Система містить кілька сутностей з чіткими бізнес-правилами (користувачі, групи, предмети, заняття, оцінки). Потрібно запобігти перетворенню коду на «Big Ball of Mud» (хаотичні виклики між модулями та прямі SQL-запити з будь-якого місця) та водночас уникнути надмірної складності розгортання й підтримки, притаманної мікросервісам.

## Розглянуті варіанти

1. **Модульний моноліт (Modular Monolith):**
    - Розбиття коду на ізольовані доменні модулі з власними сервісами та репозиторіями.
    - Вимагає створення проксі-методів та міжмодульних інтерфейсів для доступу до даних сусідніх модулів.
2. **Класична 3-шарова архітектура (Layered Architecture):**
    - Єдине наскрізне розділення застосунку на 3 шари: `Routes` → `Services` → `Repositories`.
    - Загальний сервісний шар та шар роботи з базою даних для всього застосунку.
3. **Мікросервісна архітектура (Microservices):**
    - Повна фізична ізоляція сервісів із власними базами даних та HTTP/gRPC мережевою взаємодією.

## Результат рішення

**Обрано варіант 2: Класична 3-шарова архітектура (Layered Architecture).**

**Обґрунтування:**

- **Простота та швидкість розробки:** Потік даних `routes` → `services` → `repositories` покриває всі потреби системи без необхідності створювати зайві дублюючі абстракції та міжмодульні проксі-сервіси.
- **Мінімальний оверхед:** Для наявного обсягу тісно пов'язаних сутностей класичні 3 шари дозволяють писати простіший і зрозуміліший код із прямою навігацією.
- **Чітке розділення обов'язків:**
    - `routes` — прийом HTTP-запитів, валідація вхідних даних, повернення відповідей та помилок.
    - `services` — бізнес-логіка, перевірка прав, підрахунки та перевірка зв'язків.
    - `repositories` — виконання SQL-запитів до бази даних.

## Наслідки

**Позитивні:**

- **Низький поріг входження:** Проста та прозора структура проєкту, яку легко читати та підтримувати.
- **Мінімальна кількість шаблонного коду (boilerplate):** Не потрібно писати міжмодульні адаптери або проксі-методи.
- **Легкість тестування:** Сервісний шар та репозиторії легко покриваються юніт- та інтеграційними тестами.

**Негативні:**

- **Спільне середовище даних:** Шари мають доступ до всіх таблиць БД, що вимагає самодисципліни та перевірок на Code Review для запобігання неконтрольованим викликам між репозиторіями.
