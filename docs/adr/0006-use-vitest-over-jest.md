# [ADR-0006] Використання Vitest замість Jest

- **Статус:** Прийнято (Accepted)

## Контекст та постановка проблеми

Для завдання 3 потрібні unit-, інтеграційні та E2E-тести, покриття гілок із порогами та мутаційне тестування. Проєкт написаний на TypeScript з ESM. Наявний Jest тестував скомпільований `dist/`: перед кожним прогоном потрібна збірка, покриття рахується по JS, а не по `src/`. Unit-тести сервісів вимагають мокати ESM-модулі (репозиторії, інші сервіси).

## Розглянуті варіанти

- **Варіант 1: Залишити Jest як є** (тести на JS імпортують `dist/`).
    - Плюси: нічого не змінювати, Jest уже налаштований.
    - Мінуси: тест бачить лише зібраний код, покриття й мутації рахуються по `dist/`; ESM-моки лише через експериментальний `jest.unstable_mockModule` із динамічними імпортами.
- **Варіант 2: Vitest.**
    - Плюси: нативна підтримка TypeScript і ESM, імпорт `src/*.ts` без збірки проєкти (`unit`, `smoke`, далі `integration`, `e2e`) в одному конфігу; офіційний `@stryker-mutator/vitest-runner`.
    - Мінуси: нова залежність (тягне Vite); API схожий на Jest, але не ідентичний; Vitest не перевіряє типи тестів — для цього окремий `tsc -p tests/tsconfig.json`.

## Рішення та обґрунтування

**Обрано Варіант 2 (Vitest), тому що** він закриває всі чинники без обхідних шляхів: тести працюють з `src/` напряму, ESM-модулі мокаються штатно, покриття і пороги налаштовуються в одному файлі, а Stryker має для нього офіційний раннер. Варіант 1 залишає ESM-підтримку в експериментальному режимі Node, що ускладнює саме ті частини, заради яких змінюється інструмент (моки та мутаційне тестування).

## Наслідки

- **Позитивні наслідки:**
    - Тести лежать у `tests/` і не потрапляють у `dist/`; `pretest`-збірка більше не потрібна.
    - `npm run test:all` (обгортка `make test`) рахує покриття unit + інтеграційних тестів і падає, якщо воно нижче порогів зі spec.
    - Точки входу `src/server.ts` і `src/db/runSqlFile.ts` виключені з покриття: тести їх не запускають, вони перевіряються E2E-прогоном контейнера.
    - Smoke-тест і `pre-push` хук працюють без кроку збірки.
- **Негативні наслідки та ризики:**
    - Версії `vitest` і `@vitest/coverage-v8` зафіксовані точно (`4.1.12`): вони мають збігатися між собою, оновлювати їх потрібно разом.
    - Типи тестів перевіряються окремою командою `npm run typecheck:tests`; якщо її не запускати, помилки типів у тестах не будуть помічені.
