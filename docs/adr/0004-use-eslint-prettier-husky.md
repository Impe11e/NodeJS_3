# 0004. Вибір інструментів статичного аналізу та автоматизації перевірок (ESLint, Prettier, Husky)

- **Статус:** Прийнято

## Контекст та постановка проблеми

Для забезпечення високої якості коду, єдиного стилю форматування та автоматичного блокування помилок перед їх потраплянням у репозиторій необхідно обрати інструменти перевірки та Git-хуки.

## Розглянуті варіанти

1. **Ручний контроль:**
    - Відсутність локальних перевірок; розробники запускають лінтери самостійно лише перед створенням Pull Request.

2. **Автоматизований контроль через ESLint + Prettier + Husky:**
    - Використання статичного аналізу (ESLint), єдиного форматування (Prettier) та запуск хуків на рівні Git (`pre-commit`, `pre-push`).

## Результат рішення

**Обрано варіант 2:** Автоматизований контроль через ESLint + Prettier + Husky.

### Обґрунтування:

- **Захист від помилок на ранньому етапі:** Хук `pre-commit` перевіряє код за допомогою ESLint і блокує коміт при наявності синтаксичних помилок чи попереджень.
- **Контроль цілісності перед пушем:** Хук `pre-push` запускає перевірку типів TypeScript та smoke-тести, унеможливлюючи відправку зламаного коду у віддалений репозиторій.
- **Стандартизація коду:** Prettier автоматично вирівнює форматування, знімаючи суперечки щодо стилю написання коду.

## Наслідки

### Позитивні:

- Повна автоматизація циклу перевірки якості коду без ручного втручання.
- Гарантія того, що в гілку попадає лише робочий та відформатований код.
- Дотримання вимог завдання щодо налаштування хуків.

### Негативні:

- Незначне збільшення часу виконання операцій `git commit` та `git push` через виконання фонових перевірок.
