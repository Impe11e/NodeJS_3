# [ADR-0007] Docker Compose замість Testcontainers для тестового оточення

- **Статус:** Прийнято (Accepted)

## Контекст та постановка проблеми

Інтеграційним тестам потрібен справжній PostgreSQL, а E2E-тестам — ще й запущений контейнер застосунку. Spec вимагає, щоб одна команда на чистій копії піднімала БД, міграції й сервіс, запускала всі рівні тестів і прибирала оточення, а тести не залежали від `seed.sql` і порядку запуску. Команда має однаково працювати на Windows і Linux. У проєкті вже є `docker-compose.yml` і `Dockerfile` для локального запуску (`make up`).

## Розглянуті варіанти

- **Варіант 1: Testcontainers**: контейнери запускаються з коду тестів, наприклад у `globalSetup` Vitest.
    - Плюси: тестове оточення описане в TypeScript поруч із тестами; випадковий порт і адреса підключення доступні з коду; контейнери прибирає службовий контейнер Ryuk, навіть якщо процес тестів аварійно завершився; можна запускати кілька прогонів паралельно.
    - Мінуси: нова залежність; для E2E потрібен ще й контейнер застосунку, тож його збірку з `Dockerfile` і зв'язок із БД довелося б описувати вдруге в коді, окремо від наявного `docker-compose.yml`; оточення важко підняти вручну для налагодження, бо воно існує лише під час прогону; Ryuk потребує доступу до Docker-сокета.
- **Варіант 2: Docker Compose** — окремий `docker-compose.test.yml` і Node-скрипт `scripts/run-tests.mjs`, який ним керує.
    - Плюси: той самий інструмент і формат, що й `docker-compose.yml`, тож E2E додасть сервіс застосунку з наявним `Dockerfile` у той самий файл; оточення можна підняти й оглянути вручну (`docker compose -f docker-compose.test.yml up`); жодних нових npm-залежностей; конфігурація читається одним файлом.
    - Мінуси: послідовність «підняти → дочекатися → мігрувати → тести → прибрати» доводиться писати самостійно; фіксована назва проєкту `node3-test` не дозволяє запускати два прогони одночасно.

## Рішення та обґрунтування

**Обрано Варіант 2 (Docker Compose), тому що** E2E-тестам однаково потрібен Compose для застосунку разом із БД, і тримати все тестове оточення в одному форматі простіше, ніж описувати його вдруге в коді. Testcontainers виграє в автоматичному прибиранні та паралельних прогонах, але для навчального проєкту ці переваги не переважують додаткової залежності й двох різних способів описувати контейнери.

## Наслідки

- **Позитивні наслідки:**
    - Одна команда на чистій копії: потрібні лише Docker і `npm ci`.
    - Тести не залежать від `seed.sql` і стану локальної БД: кожен прогін стартує з порожньої БД з актуальною міграцією.
    - Для E2E достатньо додати сервіс застосунку в `docker-compose.test.yml`.
    - Тестове оточення можна відтворити й налагодити вручну тими самими командами `docker compose`.
- **Негативні наслідки та ризики:**
    - Прибирання залежить від того, чи дійде скрипт до `finally`: після примусового завершення потрібно вручну виконати `docker compose -f docker-compose.test.yml down -v`.
    - Паралельні прогони неможливі через фіксовану назву проєкту.
    - Docker Desktop має бути запущений; без нього команда завершується з помилкою ще до тестів.
