# [ADR-0002] Передача контексту користувача через HTTP-заголовок X-User-Id

- **Статус:** Прийнято (Accepted)

## Контекст та постановка проблеми

REST API «Електронний журнал» вимагає розмежування прав доступу на основі ролей:

- **`TEACHER`** має право виставляти та редагувати оцінки, створювати заняття.
- **`STUDENT`** має право переглядати тільки власні оцінки та розклад.

Потрібно було визначити спосіб передачі контексту ідентичності користувача у кожен HTTP-запит без ускладнення системи повноцінним сервісом авторизації (OAuth2 / Session-Cookie / JWT із хешуванням паролів).

## Розглянуті варіанти

1. **Повноцінна JWT / Session авторизація:**
    - Реалізація ендпоінтів `/login`, `/register`, хешування паролів (`bcrypt`), генерація та валідація JWT-токенів у кожному запиті.
    - Вимагає створення окремої інфраструктури для керування сесіями/токенами, що зміщує фокус розробки з бізнес-логіки журналу на безпекові механізми.

2. **Передача `X-User-Id` через HTTP Header:**
    - Ідентифікатор користувача (`X-User-Id: <user-uuid>`) передається безпосередньо в заголовках HTTP-запиту.
    - Шар `routes` витягує заголовок, а шар `services` отримує ID, завантажує профіль користувача (або витягує його з контексту) і перевіряє роль (`TEACHER` / `STUDENT`).

## Результат рішення

**Обрано варіант 2: Передача `X-User-Id` через HTTP Header.**

**Обґрунтування:**

- **Фокус на доменній логіці:** Дозволяє повністю зосередитися на бізнес-правилах журналу, не витрачаючи ресурс на написання шаблоного коду авторизації.
- **Спрощення автотестування:** Тестам (Jest / Supertest) не потрібно виконувати попередні запити авторизації для отримання токена перед кожним тестовим сценарієм. Достатньо передати необхідний `X-User-Id` у заголовку запиту.
- **Зручність тестування та відлагодження:** Полегшує ручне тестування через Postman/curl та автоматичні smoke-тести — для зміни ролі достатньо змінити значення одного заголовка `X-User-Id` у запиті.

## Наслідки

**Позитивні:**

- **Спрощення коду:** Відсутність сесій, токенів та контролерів авторизації.
- **Швидкість розробки та тестування:** Проста імітація запитів від імені студента чи викладача.
- **Архітектурна гнучкість:** У майбутньому перед сервісом можна безболісно поставити реальний API Gateway з JWT, не змінюючи бізнес-логіку в `services/`.

**Негативні:**

- **Відсутність безпеки для продакшену (без Gateway):** У публічному середовищі будь-який клієнт може підробити заголовок `X-User-Id` (Header Spoofing). Рішення прийнято виключно з розрахунком на те, що сервіс працює у захищеній внутрішній мережі або за API Gateway.
