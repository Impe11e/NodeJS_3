# Електронний журнал — специфікація

## 1. Коротко про тему

«Електронний журнал» — невеликий бекенд-застосунок для ведення обліку оцінок. Вчителі ставлять оцінки студентам за заняття зі своїх предметів, а студенти переглядають свої оцінки.

---

## 2. Критерії прийняття

- **Студент отримує лише свої оцінки:** за предметом (по заняттях) або за конкретне заняття.
- **Вчитель ставить оцінку**, лише якщо веде предмет цього заняття.
- **Оцінку можна поставити лише студенту** групи цього заняття.
- **Оцінка** — ціле число JSON від 1 до 100 (рядок, `true`, дріб не приводяться до числа й повертають `400`); для пари `(студент, заняття)` існує не більше однієї оцінки.
- **Вчитель відкриває заняття** свого предмета і бачить студентів групи цього заняття.
- **Студент отримує свій середній бал** (середнє арифметичне всіх його оцінок).
- **Студент не ставить оцінки**; вчитель не бачитиме заняття чужих предметів і не ставить за них оцінки.
- Користувача ідентифікує заголовок `X-User-Id` (авторизації немає); він перевіряється першим — за відсутнього, невалідного чи невідомого заголовка `401` незалежно від інших даних запиту. Порушення правил повертають помилку, дані не змінюються.
- **Усі id** (заголовок `X-User-Id`, тіло, path, query) мають формат UUID лише в канонічному вигляді `8-4-4-4-12` (шістнадцяткові цифри, регістр не важливий); інші записи (у фігурних дужках, без дефісів) — невалідний формат. Невалідний формат повертає `400` (для `X-User-Id` — `401`).
- **Порядок перевірок:** спершу `X-User-Id` (`401`), потім формат запиту - тіло, path, query (`400`), і лише потім бізнес-правила (`403`/`404`/`409`) у порядку кроків сценарію з розділу 5. Якщо запит порушує кілька правил, повертається помилка першого з них.

---

## 3. Структура та шари (Layered Architecture)

> **Правила:** застосунок розділено за принципом **Package-by-Layer** (`routes` → `services` → `repositories`). `routes` звертаються лише до `services`; до бази даних доступ мають лише `repositories`. Сервіс може викликати інші сервіси, але не чужі репозиторії.

| Шар              | Папка               | Відповідальність                                                                                                        |
| :--------------- | :------------------ | :---------------------------------------------------------------------------------------------------------------------- |
| **Routes**       | `src/routes/`       | HTTP-контролери Fastify. Приймають запити, зчитують `X-User-Id`, передають дані в сервісний шар та формують відповіді.  |
| **Services**     | `src/services/`     | Бізнес-логіка, валідація ролей (TEACHER/STUDENT), перевірка належності студентів до груп та обчислення середнього бала. |
| **Repositories** | `src/repositories/` | Прямий доступ до таблиць БД (`users`, `subjects`, `teacher_subjects`, `lessons`, `grades`).                             |

**Сервіси та залежності**:

| Сервіс           | Свої таблиці (через репозиторії) | Викликає сервіси                                 |
| :--------------- | :------------------------------- | :----------------------------------------------- |
| `UserService`    | `users`                          | —                                                |
| `SubjectService` | `subjects`, `teacher_subjects`   | —                                                |
| `LessonService`  | `lessons`                        | —                                                |
| `GradeService`   | `grades`                         | `UserService`, `SubjectService`, `LessonService` |

## 5. Ключові сценарії

### 1. Вчитель ставить оцінку

- **Кроки:** hook ідентифікує користувача (`UserService`) → route передає користувача й дані в `GradeService` → `LessonService` (предмет і група заняття) → `SubjectService` (чи веде вчитель предмет) → `UserService` (чи студент у групі заняття) → `GradeService` створює запис.
- **Зміна даних:** одна нова оцінка в таблиці `grades` (транзакція).
- **Успіх:** `201`, створена оцінка ([формат](./docs/api.md#post-grades)).
- **Помилки:** `400` — значення поза межами 1–100 або student_id / lesson_id не UUID; `401` — немає, невідомий або невалідний формат X-User-Id; `403` — користувач не вчитель, не веде предмет, або студент не з цієї групи; `404` — заняття не знайдено, або student_id не належить студенту; `409` — оцінка вже існує, дубль не створюється; `503` — джерело даних недоступне (БД не відповідає), дані не змінюються.

### 2. Вчитель відкриває заняття і бачить студентів

- **Кроки:** hook ідентифікує користувача → `GradeService` викликає: `LessonService` (заняття) → `SubjectService` (чи веде вчитель предмет) → `UserService` (студенти групи заняття).
- **Зміна даних:** немає (читання).
- **Успіх:** `200`, заняття зі списком студентів групи, впорядкованим за іменем ([формат](./docs/api.md#get-lessonslessonid)).
- **Помилки:** `400` — `lessonId` не UUID; `401` — немає, невідомий або невалідний формат X-User-Id; `403` — не вчитель або не веде предмет; `404` — заняття не знайдено; `503` — джерело даних недоступне (БД не відповідає).

### 3. Студент переглядає свої оцінки за предметом або за конкретне заняття

- **Кроки:** hook ідентифікує користувача → `GradeService` перевіряє фільтри: `SubjectService` (чи існує предмет), `LessonService` (чи існує заняття) → вибирає оцінки поточного студента з урахуванням фільтрів.
- **Зміна даних:** немає (читання); чужі оцінки недоступні.
- **Успіх:** `200`, список оцінок поточного студента, впорядкований за часом створення ([формат](./docs/api.md#get-grades)).
- **Помилки:** `400` — `subject_id` або `lesson_id` не UUID; `401` — немає, невідомий або невалідний формат X-User-Id; `403` — користувач не студент; `404` — предмет чи заняття не знайдено; `503` — джерело даних недоступне (БД не відповідає).

### 4. Середній бал студента

- **Кроки:** hook ідентифікує користувача → `GradeService` обчислює середнє значення всіх оцінок поточного студента.
- **Зміна даних:** немає (значення обчислюється, не зберігається).
- **Успіх:** `200`, середній бал, округлений до 2 знаків після коми; якщо оцінок немає — `null` ([формат](./docs/api.md#get-gradesaverage)).
- **Помилки:** `401` — немає, невідомий або невалідний формат X-User-Id; `403` — користувач не студент; `503` — джерело даних недоступне (БД не відповідає).

## 6. Тестування

- **Рівні:** unit - сервіс grades.service, залежності замоковані; інтеграційні - репозиторії та HTTP API з реальним PostgreSQL; E2E - сценарій «вчитель відкриває заняття → ставить оцінку → студент бачить оцінку й середній бал» через HTTP до контейнера, `/version` повертає sha поточного коміту.
- **Покриття spec:** кожен критерій розділу 2 і кожен код помилки з розділу 5 перевірено тестом; після помилки вміст БД не змінився.
- **Межові випадки:** оцінки 1 і 100; 0, 101, дріб, рядок замість числа; повторна оцінка; студент не з групи; студент без оцінок (`null`); кілька оцінок; фільтри по предмету, по заняттю й обидва разом.
- **Пороги:** src/services/grades.service.ts - 100% гілок; увесь src (крім точок входу) - ≥ 80% гілок і рядків за unit + інтеграційними тестами разом; mutation score для src/services/grades.service.ts ≥ 80%. Нижче порогу команда завершується з помилкою.

- **Мутаційне тестування:** npm run test:mutation (обгортка make mutation) запускає Stryker; кожен вижилий мутант класифіковано (реальна прогалина / еквівалентний / прийнятний).
- **Ізоляція:** тести не залежать від seed.sql і порядку запуску; БД очищується перед кожним тестом.
- **Відтворюваність:** на чистій копії npm run test:all (обгортка make test) піднімає БД, міграції й сервіс, запускає всі рівні, прибирає оточення і повертає ненульовий код при падінні.
